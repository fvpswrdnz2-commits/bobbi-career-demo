## 3. 系统边界

### 3.1 第一版包含

- 同一个微信小程序内的学生端和前辈端。
- 波比使用的独立网页运营后台。
- 前辈展示和三种搜索模式。
- 未来 7 天档期、30/60/90 分钟套餐和 15 分钟支付锁定。
- 学生简历及问题、微信支付、自动接单、改期、取消和退款。
- 腾讯会议信息人工录入与紧急提醒。
- 系统自动算账、波比人工结算。
- 旧前辈后台导入、新前辈邀请提交和审核。
- 私有文件、字段权限、审计、通知、定时任务和经营数据统计。

### 3.2 第一版明确不包含

- 群面和讲座业务页面。
- 渠道码和渠道归因。
- 多级管理员角色。
- 腾讯会议 API 和微信支付自动分账。
- 前辈自行维护档期。
- 多种咨询服务、独立套餐价格、续时和补单。
- 销量、评价、排行榜、优惠券、会员和站内自由聊天。
- Elasticsearch、向量数据库、RRF、机器学习排序或个性化推荐。
- 小程序售后反馈、售后工单和24小时售后期。

群面和讲座是后续明确方向。第一版保留统一用户 ID、订单 `business_type` 和事件 `business_type` 三个低成本稳定扩展点，但不预建未来数据模型、角色、页面、运行分支或通用接口；进入实际开发范围后再基于届时运行中的系统演进。

## 4. 计划部署拓扑

```text
微信用户
→ 微信原生小程序（学生端＋前辈端）
→ NestJS 模块化单体 API / Worker
→ PostgreSQL（业务事实＋pg-boss任务）
→ COS 私有桶（简历、证明、结算凭证）
→ 微信登录、微信支付、订阅消息

波比
→ React 运营后台
→ 同一 NestJS API

NestJS
→ CLS / 云监控
→ SSM 密钥管理
→ 短信服务（仅缺会议紧急通知波比）
```

计划采用：微信原生小程序＋TypeScript＋TDesign、React＋Vite＋Ant Design、Node.js＋NestJS、PostgreSQL＋Prisma、pg-boss、COS、CloudBase 云托管。整体为一套后端和一套主数据库的模块化单体，不使用微服务、Kubernetes 或 Redis。

### 4.1 计划拓扑的取舍理由

- 不使用微服务：预约、档期、支付、退款和结算共享强事务边界，第一版由一个团队维护；拆分服务会增加分布式事务、部署和排错成本，却没有独立扩缩容收益。
- 不使用 Redis：活动档期唯一性由 PostgreSQL 约束裁决，可靠任务由同一 PostgreSQL 上的 pg-boss 承担；当前没有数据库已被验证无法承受的热点缓存、限流或队列需求。
- 不使用腾讯会议 API：第一版真实流程已经确认由波比在腾讯会议侧创建，再由后台录入、更新或取消；预建 API 适配层会引入当前无使用者的抽象，待商业账号、成本、并发资源和接口额度确认后再演进。
- 不使用 Kubernetes：CloudBase 云托管已经承担容器运行、健康检查和弹性，第一版无需自行维护集群控制面。
- 保持模块化单体：模块边界用于限制职责和未来演进，不代表独立部署；PostgreSQL 继续作为业务事实与任务事实的共同数据源。

## 7. 身份与权限基线

### 7.1 小程序用户

- 所有微信用户使用同一个用户账号，默认具有学生能力。
- 受邀前辈审核并绑定后，同一账号增加前辈角色。
- 同一用户可以同时是学生和前辈。
- 前辈暂停或下架不影响其学生身份及历史订单访问。

### 7.2 后台管理员

- 第一版只有一个超级管理员身份，由波比使用。
- 不实现只读运营、普通运营等多级角色。
- 后台不开放注册，使用独立账号、强密码、TOTP、限速和会话过期。
- 退款、金额修正、强制改期、会议替换和结算登记需要二次确认并审计。

### 7.3 材料权限

- 前辈证明材料只对超级管理员可见。
- 学生简历在支付前只对学生本人和超级管理员可见。
- 支付成功自动接单后，只开放给对应前辈。
- 咨询结束 7 天后撤销前辈访问；90 天后删除原始简历。
- 任何文件链接都必须短时有效并在每次签发前重新鉴权。

## 8. 前辈档案与字段基线

每位前辈只保存一份档案，通过字段权限区分公开与私密信息。

公开信息包括：

- 与小红书一致的唯一投稿编号。
- 昵称、头像和脱敏届别等背景。
- 教育经历：学历、国内/海外、一个主要层次标签、公开学校名称和专业。
- 实习经历标签。
- 秋招情况标签。
- 最终 Offer 情况标签。
- 秋招心得长文本。
- 擅长咨询方向、价格和近期可约状态。

新增受邀前辈还需提交可预约时间偏好和备注。该信息用于波比配置 `AvailabilityRule`，不是公开的可售档期，也不会由提交动作直接生成档期。

第一版不建立生源地/户籍、适合咨询人群和放弃终面字段。真实姓名、联系方式、可选真实学校信息、证明材料、结算信息和内部备注只对超级管理员开放。

新增受邀前辈提交审核前至少上传一份统一证明材料；实习邮件、工牌或系统截图可以替代正式实习证明。材料不要求与每条经历逐项绑定，也不要求逐项强制核验通过。旧前辈由波比导入，免于补传证明材料。

## 9. 搜索架构基线

第一版名称为“标签匹配＋三因素加权”，只使用可公开的结构化字段和有效档期。

### 9.1 三种模式

1. 投稿编号直达：规范化“340、投稿340号、前辈 ３４０”等输入后精确查询，不参与加权排序。
2. 标签组合筛选：同维度多选取并集，跨维度取交集；明确时间和时长是硬条件。
3. 一句话搜索：使用简单标签词典，从文本中确定性识别标签、别名、时间和时长；不调用生成式 AI。

### 9.2 标签词典

每个搜索标签只保存当前需要的标准名、维度、所属业务大类和别名，不建立词典版本系统。前辈自由输入的原始标签始终保留；命中字典时另存标准标签，未知标签只参与原文精确匹配，不自动猜测业务大类。完全相同标签计 100 分，同业务大类计 60 分，无关或未命中计 0 分。歧义词不得静默归一，未知词不得臆测。

### 9.3 排序公式

```text
匹配总分 = 教育背景匹配度 × 20%
         + 求职经历匹配度 × 50%
         + 档期可约度 × 30%
```

- 教育背景包含学历和学校层次。
- 求职经历包含实习、秋招情况、最终 Offer 和擅长咨询方向。
- 档期可约度包含未来 7 天连续档期和最早可约时间。
- 用户明确选择的时间或时长不满足时直接过滤，不能靠低分进入结果。
- 同分按完全匹配标签数、最早可约时间、投稿编号升序排序；发布时间不参与排序。
- 销量、成交额、证明材料、真实身份和私密备注不参与排序。

### 9.4 匹配理由与放宽

- 每个结果展示 2—4 条由真实公开字段或档期生成的匹配理由。
- 匹配理由使用确定性模板，不使用生成式 AI。
- 完全匹配不足时可以展示相近匹配，但必须指出放宽项和未命中项。
- 时间和时长硬条件不得放宽。
- 搜索必须使用固定评测集验证，并记录三种模式、别名、硬条件和私密字段隔离结果。

## 10. 预约与档期不变量

- 可预约范围为未来 7 天，首次预约距开始至少 6 小时。
- 30 分钟为最小时间单位；30/60/90 分钟分别占用 1/2/3 个连续时段。
- 同一前辈同一 30 分钟段只能存在一个活动占位。
- 待支付订单锁定档期 15 分钟，超时关闭并释放。
- 档期冲突必须由数据库事务和唯一约束保证，不能依赖页面状态。
- 订单使用创建时的价格快照；60/90 分钟按30分钟基础价格等比例计算，第一版不单独覆盖。
- 预约时必须提交简历和非空咨询问题。
- 微信支付服务端确认后自动接单并开放对应前辈的材料访问。

## 11. 改期、取消和金额基线

### 11.1 改期

- 学生和前辈各有一次免费改期额度，次数分别累计。
- 同一方第二次改期按原始订单金额 10%处理；第三次只能取消。
- 学生第二次补付10%；前辈第二次向学生退10%。
- 改期必须在当前约定开始前至少2小时发起，并在该截止时间前得到对方确认。
- 学生第二次改期补款也必须在截止前支付成功。
- 新时间必须位于确认时起未来7天内，不受首次预约距开始至少6小时限制。
- 对方确认前原时间和原档期继续有效；换档必须原子完成。

### 11.2 取消

- 学生取消：退原始订单90%，此前学生补付的改期费默认不退。
- 前辈取消：退原始订单及学生已支付改期费的全部金额。
- 取消后释放档期、停止提醒、撤销后续材料访问并生成会议取消待办。

### 11.3 收入和结算

```text
最终净收入 = 全部有效支付 - 全部成功退款
前辈应结金额 = 最终净收入 × 80%
波比收入 = 最终净收入 × 20%
```

所有金额以整数“分”保存。资金变化只追加或冲正，不无痕覆盖。第一版系统计算，波比线下付款后在后台登记；退款中或账务异常订单不得结算。

## 12. 订单与履约状态基线

主流程：

```text
待支付
→ 已支付/待录入会议
→ 待咨询
→ 咨询中
→ 已完成
```

分支状态至少包括：支付关闭、改期申请中、待支付改期费、改期退款处理中、待更新会议、取消申请中、退款处理中、已取消、已退款和结算异常。

状态只能由后端状态机修改。定时任务和外部回调必须幂等；支付、退款、档期和订单状态不能以客户端显示为最终依据。

到达约定结束时间后，订单直接进入“已完成”，不等待24小时。结算资格和付款登记属于 `Settlements` 模块的独立状态，不改变小程序订单状态，也不向前辈端开放结算中心或金额视图。小程序不直接展示内部“待录入会议”名称：会议未更新时显示“稍后查看会议链接”，保存后显示“会议信息已更新”。

## 12.1 小程序展示称谓边界

- 内部仍保留学生、前辈角色名以及相应权限模型。
- 面向预约方的可见文案不出现“学生”；面向提供咨询一方的可见文案不出现“学生/前辈”。
- 人物展示以昵称和核心背景标签为主，需要指代时使用“对方”“咨询资料”“我的资料”。
- 改期页面只写“第二次发起改期”，取消页面只写“取消规则”。

## 13. 会议与通知基线

- 第一版支付成功后生成唯一“待录入会议”任务。
- 波比在腾讯会议侧人工创建会议，再录入会议号、可选密码和链接。
- 改期生成待更新会议任务，取消生成待取消会议任务。
- 会议信息录入或更新后自动通知学生和前辈。
- 咨询前24小时和2小时发送有意义的站内/订阅提醒。
- 咨询前2小时仍缺少有效会议时，生成后台高优先级待办，并向服务端配置的波比手机号 `18800126467` 发送紧急短信；第一版不向学生或前辈发送短信。
- “联系波比”展示微信号 `b1025493856` 并支持复制。
- 订单状态与 Outbox 事件写入同一数据库事务，消息失败不回滚订单，任务可重试且避免重复轰炸。

## 14. 数据存储基线

计划核心实体：

- `User`、微信身份、会话、角色。
- `AdminAccount`、TOTP 和管理员会话。
- `SeniorProfile`、`EducationExperience`、`SeniorTag`、`SearchTagDictionary`、`SeniorInvitation`、`EvidenceMaterial`。
- `AvailabilityRule`、`AvailabilityException`、`AvailabilitySlot`、`SlotReservation`。
- `Order`、`OrderMaterial`、`OrderMaterialVersion`、`RescheduleRequest`、`MeetingInfo`。
- `PaymentRecord`、`RefundRecord`、资金流水、`SettlementBatch`、`SettlementRecord`。
- `Notification`、`OutboxEvent`、`JobRecord`、`AnalyticsEvent`、`AuditLog`、文件元数据。

PostgreSQL 是订单、档期、资金、状态和任务的唯一事实来源。Prisma 负责常规访问，唯一约束、部分索引和关键并发规则使用 SQL migration 明确定义。数据库时间以 UTC 保存，界面按 `Asia/Shanghai` 展示。

`Order.business_type` 和业务事件 `business_type` 第一版固定为 `ONE_ON_ONE_CONSULTATION`。它们只用于稳定区分历史业务数据，不改变第一版状态机，也不得用于提前实现群面或讲座分支。

第一版用户与事件数据中不预置渠道码、首次来源或最近来源字段。

## 15. 当前外部集成边界

| 当前集成 | 第一版具体实现 |
| --- | --- |
| 微信支付 | 在 `WechatPayService` 中集中处理 API v3 签名、验签、回调、查询和退款 |

## 16. 安全与可靠性不变量

1. 金额、角色、订单状态和档期有效性只由服务端判断。
2. 支付、退款、改期确认、占位和定时任务必须幂等。
3. 同一档期的并发竞争最终由数据库约束裁决。
4. 密钥、证书和长期云凭证不得进入客户端、源码或日志。
5. COS 保持私有读，访问链接短时有效且逐次鉴权。
6. 日志不得记录简历正文、证明内容、短时链接、完整联系方式、会议密码或支付密钥。
7. 查看敏感材料、审核、强制改期、退款、金额修改、会议替换和结算均写审计日志。
8. local、staging、production 的数据库、文件、微信配置和密钥完全隔离。
9. 关键定时任务失败必须重试并告警；任务重复执行不得造成重复状态、重复退款或重复通知。
10. 搜索索引和匹配理由只能使用公开字段，证明材料和学生资料永不参与搜索。

## 17. 环境与运行基线

- `local`：本地开发，仅使用虚构脱敏数据。
- `staging`：测试小程序、测试支付、独立数据库和 COS。
- `production`：真实用户和订单，禁止复制数据到其他环境。
- 后端计划部署到 CloudBase 云托管，最小实例数保持1以保证任务运行。
- 运营后台计划部署到 CloudBase 静态托管。
- PostgreSQL 生产实例开启自动备份和时间点恢复。
- CLS 和云监控覆盖 API、任务、支付退款、缺会议、文件删除和结算异常。
- SSM 保存支付私钥、API v3 密钥、数据库密码和 TOTP 加密密钥。
